## 議論メモ

### グループ名: `bump:` vs `semver:`

最初 `tasks/bump/check-bumped.pkl` で書き始めたが、ユーザ指摘で `tasks/semver/check-bumped.pkl` に変更。

理由 (DR-0005 で詳述):
- `bump:` は「bump-semver CLI 名」と「version bump アクション」を同時に指して意味が狭い
- `semver:` (ドメイン名) なら将来 `semver:bump-version` / `semver:compare` 等の拡張を一貫して収容できる
- 他グループ (`vcs:` / `docs:` / `lint:`) もドメイン名なので流儀が揃う

### bump-semver なし fallback の不採用

最初は `command -v bump-semver` で 2 段階 dispatch (あれば `bump-semver compare gt`、なければ `vcs.readAtRef` + `sort -V`) を検討した。`sort -V` が `0.14.0-rc.1` vs `0.14.0` で直感に反する結果になることが判明し「SemVer 比較を bash で再実装するのは辛すぎる」「できないものはスパッと切る (ユーザ判断)」で fallback 自体を未実装に。`not implemented: install bump-semver` メッセージで exit 1。

### vcs/* と semver/* の責務切り分け

`semver:check-bumped` が VCS 操作 (jj/git diff) と SemVer 操作の両方を含むため「どちらのグループか」が悩ましかった。整理:

- `vcs/*` = primitive (`commit` / `push` / `diffSummary` / `readAtRef`) — 単独で意味成立
- `semver/*` = high-level gate (内部で vcs primitive を借用) — VCS 文脈と合わさって gate task になる
- 依存方向は **semver → vcs** で clean (逆依存なし)

利用者目線で「version bump gate」の顔は semver なので、`semver:check-bumped` でラベルとして正しい。

## 学び (Tips)

### `pkl format -w` は silent

`pkl format -w .` は auto-fix した場合に **出力なし**。jj diff も発生していないと「何も変わってない」と誤認しやすい。canonical form 検証は `pkl format` 後の `jj diff --stat` で確認する。

### jj workspace 内での git tag は `tag -l` で取れる、`git describe` は不可

```bash
# OK
git tag -l 'v*' --sort=-v:refname | head -1

# NG (HEAD が存在しない)
git describe --tags --abbrev=0 --match='v*'
```

`git describe` は work tree の HEAD が必要なので jj workspace では fatal: Not a valid object name HEAD。tag list ベースで取得するのが安全。

### bump-semver の `vcs:` ref schema

`bump-semver compare gt VERSION vcs:<REV>:<FILE>` で「<REV> 時点の <FILE> 内 VERSION」と現在を比較できる。`<REV>` は jj 形式 (`main@origin`) も git 形式 (`origin/main`, `v0.14.0` 等の tag) も理解する (jj/git auto-detect)。

特殊形式:
- `vcs:latest-tag()` — 最大の semver-compatible tag を VCS から取得

### bare git に tag が無い問題

`git tag -l` がローカルで `v0.14.0` までしか返さない場合、bare git の fetch が tags まで広げていないため。明示的に:

```bash
git --git-dir="$REPO_PARENT/.git" fetch --tags origin
```

`jj git fetch` だけだと tag は来ない (refspec が branches 主体)。

### pkfire composite action `@` in ref tag

`uses: mizchi/pkfire@pkfire@0.4.0` は workflow file レベル parse 失敗。`@` 1 個版 (`mizchi/pkfire@0.4.0`) も同じ理由で失敗 (tag が存在しないだけでなく `@` 入り ref を parser が嫌う)。**SHA pin 必須** (DR-0004)。

### release.yml の初回 trigger

0.0.7 で `.github/workflows/release.yml` が初めて発火した。`gh release create 'pkf-tasks@0.0.7' --target main --notes "..."` で tag + release を一気に作成 → tag push trigger で release.yml が動き、`pkl project package` → `gh release upload --clobber` で 4 assets を attach。成功。
