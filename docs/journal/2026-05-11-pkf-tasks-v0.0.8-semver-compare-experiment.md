# 2026-05-11 — pkf-tasks v0.0.8 (`semver:compare` 汎用 task 実験)

## 動機

v0.0.7 で `semver:check-bumped` を parameterized task として導入したが、ユーザから「pkfire の acceptsArgs が使えるなら `semver:compare` のような汎用 primitive を作って `pkf run semver:compare -- lt Cargo.toml vcs:latest-tag()` 的な ad-hoc 呼び出し + deps 合成にできないか」という提案。

実験スコープ:
1. `semver:compare` 汎用 task の試作
2. pkfire の `Task.deps` / `acceptsArgs` 仕様での合成可否確認
3. 使い勝手の評価 (parameterized task との比較)

## pkfire の仕様確認

`pkfire@0.4.0/Taskfile.pkl` のスキーマを直読みして以下を確認:

```pkl
class Task {
  ...
  /// Dependencies as direct Task references.
  deps: Listing<Task> = new {}
  ...
  /// When true, positional args after `--` on the pkf command line are
  /// forwarded to `cmd` as `$1` ... `$@`.
  acceptsArgs: Boolean = false
  ...
  /// Typed named flags accepted by `pkf run <task> --<name>=<value>`.
  params: Listing<Param> = new {}
}
```

加えて wire format (`RenderedTask.deps: Listing<String>`) を見ると、deps は task name 文字列のリストに展開される。つまり:

- **deps は静的 task 参照のリスト**、各エントリに引数や options を付けられない
- 引数受け取りは CLI 経由のみ (`pkf run <task> -- ...` で `$@`、`--name=value` で `$NAME`)
- cache key は CLI args / params 値も含むので、`pkf run task -- foo` と `pkf run task -- bar` は別 cache entry になる

**結論: deps での引数付き呼び出しは不可能**。`semver:check-bumped` のような複合 gate task が `deps { semverCompare(args=["gt", "VERSION", ...]) }` のように合成することはできない。pkfire の設計として deps は「order + cache key 連動」のみで、higher-order な合成 (関数呼び出し的な渡し方) は範囲外。

## 試作

`tasks/semver/compare.pkl`:

```pkl
module com.github.kawaz.pkfTasks.semver.compare
import "@pkfire/Taskfile.pkl"

compare: Taskfile.Task = new Taskfile.Task {
  name = "semver:compare"
  description = "SemVer compare via bump-semver (pkf run semver:compare -- <OP> <INPUT> <INPUT>)"
  acceptsArgs = true
  cmd = """
    if ! command -v bump-semver >/dev/null 2>&1; then
      echo 'ERROR: bump-semver not installed' >&2
      exit 1
    fi
    bump-semver compare "$@" --no-hint
    """
}
```

## 動作確認結果 (bump-semver でドッグフード)

`kawaz/bump-semver` の Taskfile.pkl に `semverCompare.compare` を追加して動作確認:

| 呼び出し | 期待 | 実結果 |
|---|---|---|
| `pkf run semver:compare -- gt VERSION 1.0.0` | 0.14.2 > 1.0.0 → false → exit 1 | ✅ exit 1 |
| `pkf run semver:compare -- gt VERSION 0.10.0` | 0.14.2 > 0.10.0 → true → exit 0 | ✅ exit 0 |
| `pkf run semver:compare -- gt VERSION vcs:v0.14.0:VERSION` | 0.14.2 > 0.14.0 → true → exit 0 | ✅ exit 0 |
| `pkf run semver:compare -- lt VERSION vcs:latest-tag()` | 比較対象 = 最大 tag | bump-semver は `vcs:latest-tag()` を jj 経由で取得、jj の tag view が `git fetch --tags` 反映遅延で v0.14.0 (古い) を返す現象あり (※ 本実験の本筋ではないが副次発見) |

cache hit も確認: 同じ `pkf run semver:compare -- <args>` の再実行は cache 経由 (`ran XXX` → 2 回目以降 `hit XXX`)。args が違えば別 cache entry。

副次発見 (bump-semver / jj の挙動):
- `vcs:latest-tag()` は jj が認識する tag を見る。`git fetch --tags origin` だけだと jj operation log に反映されない場合あり (`jj git import` で同期が必要かも)
- これは bump-semver の bug ではなく、jj の tag view 同期遅延の問題。kawaz の bump-semver リポで再現

## 使い勝手の評価

### 成立する利用形態

```bash
# ad-hoc CLI 直叩き (これは動く想定)
pkf run semver:compare -- gt VERSION 1.0.0
pkf run semver:compare -- lt Cargo.toml vcs:latest-tag():Cargo.toml
pkf run semver:compare -- eq package.json vcs:main@origin:package.json
```

### 成立しない利用形態 (期待していたが pkfire 仕様で不可)

```pkl
// ✗ deps への引数付け不可
local checkBumped = new Task {
  deps {
    (semverCompareModule.compare) { args = "gt VERSION vcs:main@origin:VERSION" }
  }
}
```

代替:
- 複合 gate task は内部で `bump-semver compare ...` を直接呼ぶ (`semver:check-bumped` の現実装と同じ)
- 利用者が CLI で `pkf run semver:compare -- ...` と `pkf run semver:check-bumped` を別個に呼ぶ運用

### 価値

- **ad-hoc 用途**: 「今すぐ手元の VERSION を最新 tag と比較したい」のようなワンショット用途に `pkf run semver:compare -- lt VERSION vcs:latest-tag()` で済む。`bump-semver compare lt VERSION vcs:latest-tag()` を直接打つのと違いは小さいが、pkf の task interface に揃えると `pkf list` で発見性が上がる、cache hit を活かせる、利用者が他の `semver:*` task と並べて記憶できる
- **bump-semver なし環境のエラー統一**: cmd 冒頭で `command -v bump-semver` チェックすることで「not implemented + install hint」を一貫して提示できる (素の bump-semver はコマンド未存在エラーで終わる)

### 限界

- **合成不能**: 複数の SemVer 比較を組み合わせた複合 gate を deps だけで宣言的に書けない (parameterized task のほうが必要)
- **pkfire 仕様変更頼み**: もし将来 pkfire が `Listing<TaskCall>` のような higher-order な deps をサポートしたら本 task の価値が高まる。現状は ad-hoc CLI 用に留まる

## v0.0.9 候補

- ドッグフーディング結果次第:
  - 使う頻度が低ければ deprecate (`semver:check-*` に統合)
  - 使う頻度が高ければ正式化 (実験的ラベルを外す)
- pkfire 上流に「`Listing<TaskCall>` 的な deps higher-order 提案」を issue として上げる検討

## 学び

### pkfire 仕様の見方

cache 配下の `pkfire@<version>.zip` を `unzip -p` で展開して Taskfile.pkl を直読みするのが最短:

```bash
unzip -p ~/.pkl/cache/package-2/pkg.pkl-lang.org/github.com/mizchi/pkfire/pkfire@0.4.0/pkfire@0.4.0.zip Taskfile.pkl
```

`class Task` / `class Param` / `class RenderedTask` のフィールド型と doc コメントが詳細で、機能の有無をソース 1 ファイルで判断できる。

### 「方針が固まる前に実装へ走るな」のバランス

ユーザの discussion-style.md に「議論を深めるための確認・調査・PoC は歓迎」とある。本実験は「PoC」枠で、仕様確認 → 試作 → 評価 → 正式化判断 の段階を踏む。実装で確かめるからこそ「使い勝手」の評価ができる (机上だけだとイメージ通りに動くかわからない)。
